Digital information display for the office lobby TV (16:9, landscape, passive/non-touch), plus an admin panel for staff to manage content.

## Tech stack

- Next.js (App Router) + TypeScript (already installed). This version differs from older Next.js: before touching routing, route handlers, caching, `revalidateTag` or the middleware/proxy file, read the matching guide in `node_modules/next/dist/docs/`
- Tailwind CSS + shadcn/ui (already installed). Add components with `npx shadcn@latest add <name>`
- PostgreSQL on Neon + Drizzle ORM (`drizzle-orm` with the Neon serverless HTTP driver; `DATABASE_URL` for the app, direct connection string as `DIRECT_URL` for drizzle-kit)
- Deployment: Vercel (serverless Next.js). Server timezone is UTC; there is no persistent local disk
- Auth.js (credentials login, single admin role)
- SWR for polling on the display page

## Commands

- `npm run dev` / `npm run build` / `npm start`
- `npx drizzle-kit generate` : create a SQL migration from schema changes (commit the result)
- `npx drizzle-kit migrate` : apply migrations
- `npx drizzle-kit push` : sync schema directly, ONLY against the dev database
- `npx drizzle-kit studio` : Drizzle Studio, a local web UI to browse and edit data (see Database rules)
- Keep `package.json` scripts `db:generate`, `db:migrate`, `db:push`, `db:studio` as shortcuts for the four drizzle-kit commands above

## Folder structure

- `app/(display)/display/` : fullscreen display page (public)
- `app/(admin)/admin/` : admin panel (login required)
- `app/api/` : routes only (thin route handlers, one line per method)
- `server/` : `controllers/`, `requests/`, `services/`, `models/`, `resources/`, `middleware/`, `errors/`, `http/` (see `docs/BACKEND.md`)
- `lib/schemas/` : shared zod schemas (used by `server/requests/` and admin forms)
- `components/ui/` : shadcn components (generated by the CLI; do not hand-edit)
- `components/display/` : display panels (header, waktu-panel, promo-panel, video-panel, pandu-panel, pengumuman-panel, agenda-panel, running-text) and `autoscroll`
- `hooks/` : `use-clock`, `use-autoscroll`, `use-prayer-mode`
- `lib/` : `config.ts` (typed env config), `location.ts` (hard-coded location), `data-sources.ts` (API endpoints, prayer method), `weather-code.ts` (WMO code to label/icon), time helpers
- `db/schema.ts` (Drizzle schema), `db/index.ts` (Neon client), `drizzle.config.ts`, `drizzle/` (generated migrations)
- No uploads in this app: media (images, video, logos, QR) is hosted elsewhere and stored as URLs in the database

## Layout and styling rules (from docs/LAYOUT.md)

- Layout: CSS Grid. Screen rows `10% 85% 5%`, main columns `2fr 6fr 4fr`. Row splits inside a column use `fr` (not `%`), because percentage rows plus `gap` overflow. No scroll on the main layout.
- No hard-coded sizes or colors. Use design tokens (CSS variables) defined once in `app/globals.css`.
- Size tokens: `--rows-*`, `--cols-main`, `--gap`, `--pad`, `--pad-x`, `--icon`, `--fs-clock`, `--fs-title`, `--fs-body`, `--fs-badge`, `--fs-countdown`, `--fade-mask`.
- The panel radius token is `--radius-panel`. NEVER redefine `--radius`: shadcn owns it.
- Color tokens use the `--c-*` prefix (bg, panel, border, text, muted, accent, highlight, azan-bg, badge, band, on-band). Values come from `docs/DESIGN.md` through the mapping in LAYOUT.md section 3, approved in T2. Do not use raw Tailwind palette classes (`bg-slate-100`, `bg-emerald-100`) on display panels.
- Tailwind arbitrary values with variables: `text-[length:var(--fs-title)]`, `p-[var(--pad)]`, `rounded-[var(--radius-panel)]`, `grid-rows-[var(--rows-right)]`.
- Every grid/flex container with dynamic content gets `min-h-0`.
- Absolute positioning only for decorative overlays (badges, gradients, play button), never for main panels.
- Video: `aspect-video` + `object-cover`. Images: `object-contain` for promo/infographics.

## Design system (docs/DESIGN.md)

- `DESIGN.md` is a style reference extracted from a marketing website. Use it for palette, font families, radius and shadow style, and the card look. Do not use its marketing type scale (64 to 96 px headlines), page layout (1200 px max width, sticky nav, hero bands), buttons, nav components or imagery on the display. LAYOUT.md tokens control size and layout, because the TV is read from a distance.
- Never paste DESIGN.md's "Quick Start" `:root` or `@theme` blocks into `app/globals.css`. Its `--spacing-*` entries would redefine Tailwind's spacing utilities (`p-4` would become 4px) and break shadcn components, its `--radius-*` entries collide with shadcn's radius scale, and `--section-gap` and `--element-gap` hold invalid values (`80-100px`). Take only the colors mapped to the `--c-*` tokens.
- The named Salesforce fonts are proprietary and not used. Use the free substitutes listed in DESIGN.md through `next/font` (final choice in T2). Do not copy the Slack name, logos or imagery.
- No gradients on surfaces. The only gradient is the `--fade-mask` on scrolling panels.

## Behavior rules

- The display is passive: no buttons, no "Lihat" cues, no manual-scroll handling. Panels auto-scroll only.
- Time comparisons use seconds since midnight in the configured timezone (`DASHBOARD_TIMEZONE`), never the device timezone.
- Display must never go blank: keep last good data (memory + localStorage) if a fetch fails; hide a slide whose data is missing instead of showing errors.
- Clean up every timer, interval, observer and requestAnimationFrame in hook cleanups (the page runs 24/7).
- Prefer server components; use client components only for interactivity (clock, carousels, autoscroll, polling).
- Content (names, announcements, agenda, etc.) comes from data/config, never hard-coded in markup. The one deliberate exception is the location constant below.
- Location is hard-coded once in `lib/location.ts`: name "Kota Dumai", latitude `1.66711`, longitude `101.44316`. Prayer times and weather always use this constant (by coordinates, never by city name). Do not read the location from env vars, the database or the admin panel, and do not repeat the numbers anywhere else.

## Vercel + Neon rules

- Never write files to disk at runtime (Vercel's filesystem is read-only/ephemeral). The app has no upload feature: media fields are URL strings.
- Media URLs must be `https` and point directly to the file (image or mp4). Validate them in admin forms (zod) and show a preview. The display uses plain `<img>`/`<video>`, not `next/image` optimization (avoids per-host config and Vercel image quota).
- A broken media URL must never break the display: on load error, skip that item (or show the fallback image).
- All date logic uses `DASHBOARD_TIMEZONE` (e.g. `Asia/Jakarta`), never the server's local time.
- Protect the database: the display polls every 60 seconds, 24/7, and Neon bills compute time while awake. `/api/display` must be served from the Next.js cache (tagged, with the current date in the config timezone as part of the cache key) and revalidated with `revalidateTag` when admin changes data. Do not query the database on every poll.
- Auth.js uses JWT sessions. Do not import the database client in the Next.js middleware/proxy file (`middleware.ts` or `proxy.ts`, depending on the installed version).
- Database: Drizzle schema lives in `db/schema.ts`. Use `drizzle-kit generate` + `migrate` for committed migrations; `drizzle-kit push` only against the dev database. Dev and production use separate Neon branches or projects. The HTTP driver has no interactive transactions; if one is needed, ask before switching drivers.
- `drizzle.config.ts` must load env from `.env.local` explicitly (drizzle-kit runs outside Next.js and does not read Next's env files on its own) and use `DIRECT_URL`.
- Drizzle Studio (`npm run db:studio`) is a local tool with full read/write access. Run it against the dev database. Never deploy it. Production data is managed from the admin panel; touching production through Studio is a deliberate, manual act.
- Keep all secrets in Vercel environment variables; keep `.env.example` updated.

## Backend layers

- Flow: route -> middleware -> request -> controller -> service -> model -> resource. Follow `docs/BACKEND.md` exactly.
- Routes contain no logic. Controllers contain no business rules and never import `db`. Only models touch the database. Services never use HTTP types. Calls only go downward.
- All input is validated through a request and a zod schema from `lib/schemas/`. Admin routes use `with-auth` (default deny). No Server Actions.
- Every write goes through a service that revalidates the display cache tag.
- Build `running-text` end to end first as the reference entity, then copy its structure for every other entity.

## Third-party data (prayer times, weather)

- Prayer times (AlAdhan) and weather (Open-Meteo) are fetched ONCE on initial page load, directly by the browser. They are never part of the 60-second polling, and there is no `/api/sholat` or `/api/cuaca` proxy (if CORS blocks a call, stop and ask first).
- Build the request URLs from `lib/location.ts` and `lib/data-sources.ts`; never repeat the coordinates in code. Dates are formatted in `DASHBOARD_TIMEZONE`.
- A failed fetch retries with backoff; the last good result is cached in localStorage. Details, endpoints and the weather-code table: `docs/DATA-SOURCES.md`.

## shadcn first

- Every UI element is built on a shadcn/ui component whenever shadcn has an equivalent (card, badge, avatar, aspect-ratio, separator, scroll-area, carousel, button, input, form, table, dialog, sidebar, and so on).
- Before writing any UI, check whether shadcn has it (https://ui.shadcn.com/docs/components, or run `npx shadcn@latest add` to browse). If it does and it is not yet in `components/ui/`, install it FIRST with `npx shadcn@latest add <name>`, then compose it. Never hand-write an equivalent.
- If shadcn has no equivalent (clock, autoscroll behavior, prayer-mode logic, marquee, crossfade slide stack), write a custom component, composed from shadcn primitives and `cn` where possible.
- Do not hand-edit files in `components/ui/`. Adapt through `className` in wrapper components (`components/display/`), using tokens (`--pad`, `--radius-panel`, `--fs-*`, `--c-*`). If a shadcn default (padding, gap, border, shadow, radius) fights the tokens, override it there. If the shadcn component itself must change, ask first.
- Never change shadcn's `--radius`. Mapping shadcn's color variables (`--primary`, `--ring`, etc.) to the emerald palette is allowed only in T2, after the user approves the palette.
- Record every shadcn component added in `docs/PROGRESS.md`.

## Skeleton first

- Build the layout as a component skeleton before any data or behavior. Follow `docs/COMPONENTS.md` exactly: file names, component tree, props and placeholder rules.
- `DisplayScreen` is the only component that knows the grid. Panels never set their own outer size; they fill their grid cell.
- A skeleton component has: the final structure and token-based classes, optional typed props with placeholder fallbacks, no fetching, no timers, no `'use client'`.
- Later tasks fill panel internals only. Do not restructure the grid or rename components without asking.

- Do not add features outside `docs/SPEC.md`. Ask first.
- Follow the "shadcn first" rules above for display and admin alike.
